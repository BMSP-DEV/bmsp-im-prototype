# IM2 Prototype

Prototype สำหรับปรับ UX/UI ของระบบจัดการ Incident และ Ticket ของทีม SOC ที่ดูแลลูกค้าหลายราย
ข้อมูลทั้งหมดเป็นข้อมูลจำลอง อยู่ในหน่วยความจำของเบราว์เซอร์ และกลับเป็นค่าเดิมเมื่อรีโหลด

## วิธีเปิด

```bash
npm install
npm run dev
```

เปิด http://localhost:5173 สลับมุมมอง SOC หรือลูกค้า และโหมดสว่างหรือมืด ได้จากปุ่มบัญชีมุมขวาบน

โค้ดรุ่นก่อนหน้าเก็บไว้ที่ `archive/v1/src` ถึง `archive/v4/src` ไม่ได้ถูกนำมา build

## โครงการใช้งาน

| หน้า | งานที่รองรับ | รูปแบบ |
| --- | --- | --- |
| งาน | ไล่เคสในกะ: ดู ตัดสินใจ ไปเคสถัดไป | 2 แผง คือคิวเรียงตามความเร่งด่วน (แท็บมุมมองนำด้วยตัวเลข และชิปลูกค้า) กับรายละเอียดเคส |
| เคส | สืบค้น รายงาน Export แก้หลายเคส | ตัวเลขสรุป 4 ใบ และตารางเคส กรองและเลือกคอลัมน์ได้ |
| หน้าเคส | อ่านและจัดการเคสแบบเต็มจอ | สรุปจาก AI หรือ SOP และเวลา SLA ด้านบน, กรอบซ้ายคือแท็บตัวบ่งชี้ ข้อมูลเคส ผู้เกี่ยวข้อง Log ดิบ, กรอบขวาคือ Timeline และสนทนา จอแคบรวมเป็นกรอบเดียว |
| SLA | ดูภาพรวมและลูกค้าที่เสี่ยง | ตัวเลขสรุป ตารางลูกค้า กราฟ MTTD และ MTTR |
| ลูกค้า | ตั้งค่ารายลูกค้า | หน่วยงาน SLA และการส่งเคสอยู่ในหน้าเดียว แสดง template ที่ลูกค้าได้ |
| Template | กำหนด template รายงานและเมลที่เดียว | เลือกลูกค้าจากปุ่ม เห็นว่าได้ตัวไหนและเพราะอะไรจากแถบลำดับ, ตาราง template พร้อมกติกาและลูกค้าที่ได้ในแถวเดียว, ตัวอย่างผลลัพธ์อยู่ด้านขวาตลอด |
| IoC | ค่าที่ส่งจาก Isolate | ตารางพร้อมตัวกรอง |

ปุ่มลัด: `J` `K` เลื่อนเคส, `A` รับงาน, `S` ส่งให้ลูกค้า, `/` หรือ `Ctrl K` ค้นหาเคส IP Hash ลูกค้า และคำสั่ง ปุ่มลัดตัวอักษรเดียวปิดได้จากเมนูบัญชี

## ระบบการออกแบบ

ใช้งาน Reeve (Dribbble) เป็นแนวทางด้าน layout และ interaction เท่านั้น ชื่อ เนื้อหา และภาพเป็นของ IM2

| เรื่อง | แนวทาง |
| --- | --- |
| โครงแอป | แถบเมนูไอคอนซ้าย, แถบบนมีตัวเลือกลูกค้าและช่องค้นหา |
| สีพื้น | มืดเป็นหลัก สลับสว่างได้ พื้น ตัวอักษร เส้น และปุ่มหลักใช้ค่าจาก Keycloak login theme (`bmsp-im-infra/keycloak/themes/soc`) |
| สีความหมาย | น้ำเงินสำหรับรายการที่เลือกและลิงก์ แดง ส้ม เหลือง เขียวสงวนให้สถานะ จึงไม่ใช้แดงแบรนด์ของหน้า login เป็น accent |
| ป้ายสถานะ | พื้นอ่อนมีจุดสี ยกเว้นระดับวิกฤตเป็นสีแดงทึบ |
| ฟอนต์ | Noto Sans Thai สำหรับข้อความ, JetBrains Mono สำหรับเวลา รหัส IP Hash |
| เอกลักษณ์ | แถบ SLA ที่หดตามเวลาที่เหลือ บนการ์ดคิวและในตาราง |
| จุดเด่นของแต่ละหน้า | เคส: รันเวย์ SLA, หน้าเคส: หน้าปัดนับถอยหลังและคลื่น event, SLA: แผนที่ปริมาณเคส 24 ชั่วโมง |
| Motion | ใช้แบบ Corporate ไม่เด้ง เดินแบบ linear เฉพาะสิ่งที่เป็นเวลาจริง และปิดได้ด้วย prefers-reduced-motion |
| พอดีจอ | ตั้งแต่จอ 1440×900 ขึ้นไป ทุกหน้าพอดีจอและตัวหน้าไม่เลื่อน เลื่อนได้เฉพาะในกล่องรายการยาว เช่น คิวงาน ตารางเคส เนื้อหาในแท็บ จอเล็กกว่า 1024×700 และมือถือเลื่อนหน้าตามปกติ |
| ลูกค้าจำนวนมาก | รันเวย์ SLA และแผนที่ปริมาณเคส 24 ชั่วโมงมีไม่เกิน 6 แถว 5 รายที่เสี่ยงที่สุดหรือเคสมากที่สุดได้แถวของตัวเอง ที่เหลือรวมในแถวสุดท้าย กดรหัสลูกค้าบนรันเวย์เพื่อดูเฉพาะรายนั้น |
| Scrollbar | แสดงตลอดเพื่อให้รู้ว่ารายการยังไม่จบ พื้นที่จับ 12px แถบ 6px คอนทราสต์อย่างน้อย 3:1 ลากแล้วเป็นสีน้ำเงิน เมนูและช่องแคบใช้แบบบาง 8px |
| ตารางเคส | เลื่อนได้ทั้งสองแกนในพื้นที่เดียว แถบแนวนอนอยู่ท้ายหน้าจอเสมอ หัวตารางและคอลัมน์เคสตรึงไว้ |
| กันส่งผิดลูกค้า | กล่องรหัสลูกค้าแสดงเด่นทุกจุดที่ข้อมูลจะออกจาก SOC |
| ปุ่มหลัก | มีจุดเดียว เปลี่ยนตามขั้นของเคส: รับงาน, ส่งให้ลูกค้า, ปิดเคส, Re-Open |

## การเลือก template

| เรื่อง | กติกา |
| --- | --- |
| ที่เก็บ | template รายงานและเมลอยู่ในคลังเดียว ใช้ซ้ำได้กับทุกลูกค้า |
| การเลือก | กติกาที่เจาะจงกว่าชนะ: ลูกค้า › Partner › Log source › ค่าเริ่มต้น กติกาที่ระบุสองอย่างชนะกติกาที่ระบุอย่างเดียว |
| ตอนส่งเคส | ระบบเลือกให้พร้อมบอกเหตุผล เปลี่ยนได้เฉพาะครั้งนั้น และบันทึกว่าส่งด้วย template ไหน ตัวอย่างเมลแสดงผู้ส่ง ผู้รับ หัวเรื่อง เนื้อหา และไฟล์แนบแบบที่ลูกค้าได้รับ กดแก้ไขเพื่อปรับข้อความเฉพาะครั้งนั้นได้ ระบบเก็บข้อความที่ส่งจริงไว้กับการส่งครั้งนั้น |

## กติกา SLA ที่ตกลงแล้ว

| เรื่อง | กติกา |
| --- | --- |
| การนับ | MTTD นับจาก Detect ถึงส่งเมล, MTTR นับจากส่งเมลถึงปิดเคส |
| รอลูกค้าตอบ | MTTR หยุดนับ และไม่ถูกนับว่าใกล้หมด SLA |
| Re-Open | นับต่อจากเวลาที่ปิด ไม่นับช่วงที่เคสปิดอยู่ ถ้าปิดก่อนส่งให้ลูกค้าจะนับ MTTD ต่อ |
| ถอยสถานะ | ไม่ล้างเวลาเดิม MTTD คงค่าจากการส่งครั้งแรก และ MTTR นับต่อ |

## สิ่งที่สมมติไว้ รอยืนยัน

- เมื่อลูกค้าตอบ Comment สถานะกลับเป็นส่งลูกค้าแล้ว และ SLA นับต่ออัตโนมัติ ถ้าไม่กลับเอง นาฬิกาจะค้างได้ตลอด
- เคสที่เกิน SLA ไปแล้วก่อนหยุดนับ ยังแสดงว่าเกินอยู่
- มี "บันทึกภายใน SOC" ที่ลูกค้าไม่เห็น ซึ่งไม่อยู่ใน requirement แต่จำเป็นเมื่อลูกค้าเข้ามาอ่านเคสเดียวกัน
- หน้าต่างปิดเคสมีตัวเลือกแจ้งสรุปให้ลูกค้าในสนทนา ซึ่งไม่อยู่ใน requirement
- คลื่น event บนการ์ดสรุปและปริมาณเคสรายชั่วโมงต้องมีข้อมูลรายนาทีและรายชั่วโมงจากระบบจริง ตอนนี้เป็นข้อมูลจำลอง
- ผลสรุปตอนปิดเคสคือ True Positive, False Positive, Benign
- การเข้ารหัสใช้ AES-256 และกติการหัสผ่าน 3 แบบเป็นตัวอย่าง
